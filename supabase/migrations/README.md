# Praveen Garments — Phase 1 Database Migrations

These three SQL files set up the complete Phase 1 foundation in Supabase.
They are **non-destructive** (no drops/truncates of existing data) and
**idempotent** where practical (re-running a file is safe).

## How to apply (manual, via Supabase Dashboard)

1. Open https://supabase.com/dashboard → your project
2. Go to **SQL Editor** → **New query**
3. Open `0001_core_schema.sql`, copy **the entire file**, paste into the editor, click **Run**.
   - Expected result: `Success. No rows returned` plus a final informational result row
     showing table counts (`branches 0, profiles 0/1, role_permissions 64, company_settings 1, app_settings 8`).
4. Repeat for `0002_rls_policies.sql` (expected: success + policy list).
5. Repeat for `0003_storage.sql` (expected: success + bucket row).

> ⚠️ Apply them **in order** (0001 → 0002 → 0003).

## Recommended Supabase project settings (Dashboard)

Because this is a **private** application, after applying the migrations also check:

- **Authentication → Sign In / Up → "Allow new users to sign up" → OFF**
  (there is no public signup; accounts are created only by the Admin inside the app.
  Turning this off hard-blocks the signup API endpoint as defense-in-depth.)
- **Authentication → URL Configuration**: add the app URL(s) to **Redirect URLs**
  so password-reset email links work.
- Email delivery for password resets requires SMTP to be configured under
  **Authentication → SMTP** (or keep Supabase's built-in mailer for low volume).

| `0010_phase4_active_filter_fix.sql` | **Fix (run right after 0009)**: recreates `customers_page` / `suppliers_page` with `array_append` for the active/inactive predicates. The 0009 form `v_where := v_where \|\| 'c.is_active'` (text[] \|\| unknown-typed literal) lets some PostgreSQL versions resolve `\|\|` as text concatenation instead of array append, then fails the text→text[] assignment cast with 22P02 "malformed array literal" — the search filters worked (format() returns typed text) while active/inactive filters 400'd. Same signatures, same grants; no table/data changes. |
| `0011_phase4_statement_till_payments.sql` | **Fix (run after 0010)**: recreates `customer_statement` so the closing balance credits payments made at the till. 0009 built the ledger from bills + `customer_payments` receipts + return credits only, so POS checkout payments (`sale_payments` written by `create_sale`) never reduced the statement — it overstated real dues by exactly the till-paid amount (₹1,418 shown vs ₹618 actual). Till payments are credited as a new `'till_payment'` line (doc = the sale it settled) and folded into the opening balance; the `sale_payments` mirrors of payments-ledger receipts (reference = CR receipt number, or method 'Store Credit') are excluded so nothing double-counts, `is_credit` marker rows are never credited, and only payments on COMPLETED sales count. Same signature, same grants; no table/data changes. |
| `0012_phase5_reporting.sql` | **Phase 5 reporting layer (run after 0011)**: 11 index additions matching real report/lookup access patterns (status+date composites on sales/purchase invoices, sales.location_id, sale_payments.created_at, stock_balances location-leading, expenses method/location/status+date, partial dues indexes); internal `variant_unit_costs()` (weighted-average purchase cost per variant, net of tax and purchase returns, current-cost fallback); 17 report RPCs — `dashboard_summary` (permission-scoped sections), `sales_report`, `product_sales_report`, `catalog_performance_report`, `payment_report`, `gst_report`, `profit_report` (labelled COGS estimate), `stock_valuation_report`, `stock_performance_report` (fast/slow/dead), `purchase_report`, `supplier_report`, `customer_report`, `expense_report`, `returns_report`, `cash_report` (ledger-derived daily cash), `audit_page` (admin viewer). All database-side aggregation, timezone-correct date boundaries from `company_settings.timezone`, permission-gated (`view_reports` / `view_audit_logs` / per-section dashboard permissions), grants revoked from public/anon. No table/data changes; additive and idempotent. |
| `0013_sales_report_payment_status.sql` | **Fix (run after 0012)**: recreates `sales_report` with a `p_payment_status` filter (PAID / PARTIALLY_PAID / DUE; invalid values ignored, same lenient pattern as `p_status`). The Phase 5 frontend sends `p_payment_status` on the Sales report page, but 0012's 14-arg `sales_report` does not accept it, so PostgREST cannot match the function (PGRST202) and the page shows "Could not load this report" — misread as "migration not applied" — even with 0012 deployed. The signature changes 14 → 15 args, so the 0012 version is explicitly dropped first (CREATE OR REPLACE alone would leave a second overload); the body is otherwise byte-identical to 0012 PART 4 with the same permission gate and grants. Callers that omit the new argument are unaffected (default null = no filter). No table/data changes. |
| `0014_phase6_report_exchange_cash.sql` | **Fix (run after 0013)**: Phase 6 audit finding — exchange money was asymmetric in the money reports. Exchange REFUNDS (customer paid less on a downgrade swap) were counted in `payment_report.refunds` and `cash_report.cash_refunds`, but exchange COLLECTIONS (customer paid more on an upgrade swap) were missing from `payment_report` inflows and `cash_report.expected_cash`, so a day with upgrade exchanges understated the drawer and end-of-day reconciliation could not balance. Recreates both functions with the same signatures and permission gates: `payment_report` gains an `exchange_collections` section (per method), a `summary.total_exchange_in` key, and includes positive non-Store-Credit exchange differences in `inflows` / `total_inflow`; `cash_report` gains `cash_exchange_in` (Cash differences collected during the day), includes it in `total_in` / `expected_cash`, and carries prior-day collections into `opening_cash`. No table/data changes. |
| `0015_phase8_ist_date_boundaries.sql` | **Fix (run after 0014)**: Phase 8 Part 19 audit finding — the page/list RPCs (`sales_page`, `purchase_orders_page`, `purchase_invoices_page`, `purchase_returns_page`, `sales_returns_page`, `exchanges_page`, `payments_page`) and `customer_statement` anchored calendar-date filters at the SESSION timezone (UTC on Supabase): `(p_date_from::timestamptz)` = 00:00 UTC = 05:30 IST, while the 0012 report RPCs anchor at the store timezone (`company_settings.timezone`). The two conventions disagreed for records created 00:00–05:29 IST, so the same filter could show different rows on a page vs its report. All eight functions are recreated with store-timezone-anchored boundaries (`(p_date_from::timestamp at time zone v_tz)` / `((p_date_to + 1)::timestamp at time zone v_tz)`) — filter semantics stay `[from 00:00, to+1 00:00)`, the To date remains inclusive of the whole store-local day for every module. Same signatures, same grants (re-issued verbatim); no table/data changes; additive and idempotent. |
| `0016_phase8_search_attributes.sql` | **Fix (run after 0015)**: Phase 8 Part 3 audit finding — the user-reported "some searches may not be working correctly". `pos_search()` (POS product/scan search) matched name / product_code / SKU / barcode / QR only, and `products_page()` (catalog list) matched name / product_code / variant SKU/barcode/QR only — neither ever matched **color, size, brand, category or subcategory names**, the everyday search terms of a garments shop ("Blue", "XL", a brand, a category all returned 0 rows; size matched only accidentally when the SKU text contained it). `pos_search` now also matches its already-joined size (`s`), color (`c`), brand (`b`), category (`cat`) names plus a new subcategory (`sub`) join; `products_page` now also matches category (`c`), subcategory (`sc`), brand (`b`) names plus size (`vsz`) / color (`vcol`) names inside the variant EXISTS — and its filtered COUNT query gains the same three LEFT JOINs its rows query already had (both share one WHERE string). All matching stays database-side, case-insensitive, partial and bounded. Same signatures, same grants (re-issued verbatim); no table/data changes; additive and idempotent. |

| `0017_phase11_purchase_tax_fix.sql` | **Fix (run after 0016)**: Phase 9 P9-BUG-2 — purchase invoice tax double-count. `create_purchase_invoice` (0009) accumulated `v_subtotal` from the LINE totals (tax-inclusive amounts in both tax modes) and then computed `grand_total = subtotal - discount_total + tax_total`, so the tax was ADDED on top of a subtotal that already contained it (and line discounts were subtracted a second time). Both modes were wrong (10 x 600 @ 12%: inclusive stored 6642.86 instead of 6000; exclusive stored 7440 instead of 6720), purchase orders showed 6720 for the same items, and purchase-return credits (line-proportional) proved the invoice payable was the inconsistent figure — supplier payables were overstated by roughly one tax amount per invoice. The app never sends `tax_mode`, and the RPC silently fell back to the POS *sales* `default_tax_mode` ('inclusive') — a customer-price convention leaking into a supplier cost document. The fix (same signature, same gate, item-line math untouched — it was always correct): (1) `grand_total = Σ line_total` in BOTH modes (inclusive = costs contain GST; exclusive = GST added on top), exactly the value return credits and FIFO payments are computed against; (2) `subtotal = Σ gross` (pre-discount cost base, the purchase-order convention — a PO and its PI now agree); (3) purchases default to `tax_mode 'exclusive'` (cost + GST on top, matching the purchase UIs); explicit payload `tax_mode` is still honoured. Includes an idempotent data repair: every non-CANCELLED invoice gets its document totals recomputed from its item rows; RECEIVED invoices additionally get `due_amount = grand - paid - return credits` (floor 0) and the engine-convention payment status; `paid_amount` is NEVER rewritten (real payments) — for fully-paid historical invoices the recorded over-charge stays visible as paid > grand, while the reports (which sum `grand_total`) become correct. No tables/columns/RLS/signatures change; grants re-issued verbatim. |
